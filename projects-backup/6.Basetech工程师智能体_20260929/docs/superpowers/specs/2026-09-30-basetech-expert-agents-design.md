## 1. 背景与目标

### 1.1 背景

Base Tech SWRS DHU 是一份 1572 页的平台级软件需求规范，覆盖车辆配置、诊断平台、数据链路层、信息安全、UDS 诊断服务、软件下载、AUTOSAR BSW 七大簇，已切分为 1999 条需求与 20 卷 RAG 语料。

现需基于该语料构建 **Basetech 工程师智能体**：一个面向工程师的**全流程助手**，支持问答、评审、生成三类任务。

### 1.2 目标

- 拆出一组**领域专家 Agent**，每个专家对应文档中一个可独立检索、可独立判断的技术域；
- 专家**只负责"从语料中给出有出处的判断"**，不负责输出形态；
- 由**编排层**决定派发哪些专家、如何汇总，并独占产出文件的写权限。

### 1.3 非目标（明确不做）

- **不做需求问答以外的对话**（闲聊、通用汽车知识、非 SWRS 覆盖范围的工程问题）；
- **不做语料本身的再加工**（语料已定稿；本设计只读不写语料）；
- **不做自动化提交/发布**（产出物落 `_out/`，由人工取用）；
- **不做多语言**（文档为英文，交互为中文，产出为中文+英文原文引用）。

### 2.3 平台约束（Claude Code，已核实）

- 自定义 subagent 定义于 `<project>/.claude/agents/*.md` 或 `~/.claude/agents/*.md`；
- frontmatter 字段：`name`（必需）、`description`（必需）、`tools`（可选）、`model`（可选：`inherit`/`sonnet`/`opus`/`haiku`）、`color`、`effort`；
- **支持嵌套 subagent，默认深度上限 3**（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`）——故「编排者」可以是 subagent；
- 编排者通过 `tools: Agent(a, b, c)` **限定可派发名单**，实现确定性路由；
- 并发 subagent 上限默认 20；
- 官方对动态工作流的规模建议为「medium — 尽量少于 15 个 Agent」；
- **subagent 无法向用户提问**——需要澄清时必须由主 Agent 完成。

### 2.4 方案选型过程

曾评估三套拆分方案：

| 方案 | 边界 | Agent 数 | 结论 |
|------|------|---------|------|
| A｜文档对齐 | 文档章节 4.1–4.7 | 7 领域 | 否决：DTC（39.4%）在 `4.5` 内无独立专家；`4.3` 一章横跨 CAN/Ethernet/FlexRay/LIN/A2B/LVDS，命中合计 1167 条，交给单一 Agent 不合理；`4.5`/`4.6` 边界模糊（刷写本身是 UDS 服务序列） |
| **B｜能力簇对齐** | 工程师任务对象 | **11 领域** | **采用**：边界与工程师实际提问粒度一致，问答准、评审可跨域 |
| C｜职能优先 | 不设领域层 | 0 领域 | 否决：Persona 差异只在职能不在领域，DTC/UDS/刷写的判据无法固化 |

方案 B 的领域数经两轮调整：初版 12 个，其中 `FlexRay`（109 条 / 5.5%，且逐年萎缩）经确认并入 CAN/LIN → **11 个领域**。

## 3. 架构总览

三条铁律：

1. **专家只读**——专家 `tools` 仅 `Read, Grep, Glob`，物理上无法改动语料；
2. **编排者独占写权限**——所有产出文件由编排者写入 `_out/`；
3. **结论必须可回溯**——任何判断都挂需求编号。

```
用户对话（主 Agent，唯一能与用户交互的层）
   └─ basetech-orchestrator          编排 subagent，tools 含 Agent(bt-*)
        ├─ skills/basetech/jobs/qa.md      问答：派 1–2 个专家
        ├─ skills/basetech/jobs/review.md  评审：切域 → 并行派 N 个专家 → 汇总
        └─ skills/basetech/jobs/gen.md     生成：派 1–2 个专家 → 模板化产出
                 ↓ 派发（并行）
        11 个领域专家 subagent（只读）
                 ↓ 先查 L0 索引定位，再取 L1/L2 取证
        _index/by-domain/bt-*.md     L0 定位（11 份，待生成）
        _index/meta-rules.md         元规则（编排者直判，不下发专家）
        SWRS_DHU_需求清单.md          L1 速取（871 KB，已有）
        Basetech知识库语料/           L2 取证（2.38 MB，已有）
```

**角色数对账**：15 个角色 = **12 个 subagent**（1 编排 + 11 专家）+ **3 个 Skill**。满足官方「少于 15 个 Agent」建议。

### 4.3 领域边界的刻意重叠

以下边界**故意不切干净**，因为现实问题就在交界处：

- `bt-dtc` ↔ `bt-uds`：DTC 的读取/清除本身是 UDS 服务（0x19/0x14），检测策略则属故障管理；
- `bt-flash` ↔ `bt-uds`：刷写是一组 UDS 服务的时序编排（0x34/0x36/0x37）；
- `bt-diag-transport` ↔ `bt-ethernet`：DoIP 承载于以太网；
- `bt-security` ↔ `bt-flash`：软件认证与签名在刷写流程内生效。

因此 **L0 索引允许多标签**（一条需求进多个域索引），评审工作流也会并行派发重叠域的专家，由编排者汇总时消解冲突。

### 4.4 领域合并与不设专家的决策

| 领域 | 处理 | 理由 |
|------|------|------|
| 时序/性能（346 条） | **并入** `bt-uds`（P2/P2*/S3）与 `bt-diag-transport`（传输层超时） | 时序寄生于协议，无法独立成域 |
| 功能安全（33 条） | **并入** `bt-security` 与 `bt-platform`，评审工作流作为横向检查项 | 直接命中少，但作为贯穿约束影响全员 |
| FlexRay（109 条） | **并入** `bt-can-lin-flexray` | 同属总线协议族且逐年萎缩，独立不经济 |
| 车辆配置（87 条） | **保留独立**为 `bt-carcfg` | 独立成体系（CC Master/Slave 状态机）；因体量小，列为可选并入 `bt-platform` 的候选（见 §12） |
| 文档元规则（460 / 468 / 1103 等）＋ 需求工程/文档变更 | **不设专家，归编排者** | 约束的是「该用哪份标准」而非技术实现；编排者读 `_index/meta-rules.md` 直接判定（§5.1、§12.1-1） |

## 6. 知识接入

### 6.1 三层结构

| 层 | 文件 | 体积 | 用途 |
|---|------|------|------|
| L0 定位 | `_index/by-domain/<专家>.md`（**待生成**） | 每份 4–47 KB（11 份合计约 250 KB） | 该域的「编号 + 标题 + 所在语料卷」 |
| L1 速取 | `SWRS_DHU_需求清单.md`（已有） | 871 KB | 编号 → 版本 / 验证方式 / 适用 AUTOSAR / 核心 shall 句 |
| L2 取证 | `Basetech知识库语料/SWRS_DHU_语料_XX.md`（已有） | 2.38 MB | 完整正文 |

设计意图：**避免专家全量读取 2.38 MB 语料**。多数问答在 L1 即可闭环，仅评审与深度问答下探 L2。

### 6.2 L0 索引生成

由 `_tools/build_domain_index.py`（从现有 `classify_domains.py` 扩展）生成，**关键词规则、可复跑、可审计**，采用**多标签**方案。

索引文件格式：

```md
# bt-dtc 领域索引 — DTC / 故障管理
> 由 _tools/build_domain_index.py 生成｜命中 787 条
> 取正文：在 Basetech知识库语料/ 中 Grep "^### <编号> —"

| 编号 | 标题 | 语料卷 |
|------|------|--------|
| 355 | CC Subscriber ECU configuration states | 01_355-491 |
| 356 | CC Subscriber ECU in Bulk (unconfigured) state | 01_355-491 |
```

### 6.3 索引覆盖盲区（实测，必须在生成阶段清零）

用初版关键词表对 11 个专家域试跑，结果：

- 索引条目总数 **4571**（多标签，平均每条需求落入 2.3 个域）；
- **135 条需求（6.8%）没有任何域命中** —— 即无专家认领的盲区。

盲区样例与应归属：

| 需求 | 标题 | 应归属 |
|------|------|--------|
| 1628 / 1641 / 1642 | Domain Master Address / Domain ID for IP networks / Grandmaster Clock ECU | `bt-ethernet`（gPTP 时间同步、域编号） |
| 1647 / 1648 | Nomadic Device IP Address Configuration / Range | `bt-ethernet` |
| 453 | Definition of the NetworkStatus Parameter | `bt-nm` |
| 470 / 1063 | Bus speed | `bt-can-lin-flexray` |
| 399 / 400 | Resynchronisation strategy / Sample mode | `bt-can-lin-flexray`（FlexRay） |
| 408 | Register read out using Diagnostics | `bt-uds` / `bt-dtc` |
| 1104 / 1108 | I2C start and stop conditions / Master and slave configuration | `bt-a2b-lvds` |
| 460 / 468 / 1103 | Document precedence / The priority between standard documents and this specification | **无归属**（见下） |
| 489 / 1050 / 1061 / 1069 / 1078 / 1080 / 1084 / 1160 | 各类帧/报文/校验和/端序/心跳细项 | 协议族域（需逐条判归属） |

**结论与要求**：

1. **「零无处置盲区」是 L0 索引的验收条件**，不是可选优化。生成脚本必须输出未命中清单，人工补关键词并逐条判归属，直到**每条盲区都有明确处置**——要么归入某专家域，要么登记为元规则。
2. 盲区中 460 / 468 / 1103 一类是**文档元规则**（文档优先级、标准文档与本规范的优先级），不属任何技术域。**已决：不设专家，归编排者**——生成脚本须将其抽为 `_index/meta-rules.md`，编排者在派发专家前先读该清单判定优先级（见 §5.1）。
3. 反向的**过召回**同样存在（如 `can` 会误命中 `cannot`、`candidate`）。生成脚本需用词边界匹配（`\bcan\b`）而非子串匹配，并在生成后人工抽查各域索引前 50 条。

## 7. 输出契约

| 工作流 | 派发 | 交付物 | 硬约束 |
|--------|------|--------|--------|
| `qa.md` 问答 | 1–2 个专家 | 回答 + 需求出处（编号+标题+卷）+ 原文引用 | 每个结论必须挂需求编号；无编号支撑的标「推断」；文档未覆盖则明确回答"未覆盖"，**禁止编造编号** |
| `review.md` 评审 | 编排者先切域 → 并行派 N 个专家 | 差距清单表 + 汇总报告 | 每行 = `编号｜要求摘要｜材料现状｜判定(符合/不符合/无法判定)｜依据原文`；汇总按严重度排序并标出**跨域冲突** |
| `gen.md` 生成 | 1–2 个专家 | 新需求条目 | 必须复用文档既有格式（编号占位／标题／Version／Verification Method／适用 AUTOSAR／shall 句）；必须是 shall 句式；标注「新增，编号待人工确认」 |

### 7.1 评审报告结构（固定）

```
# SWRS 合规评审报告
- 评审对象：<材料名>
- 涉及领域：<专家列表>
- 统计：符合 X ｜ 不符合 Y ｜ 无法判定 Z
## 差距清单（按严重度降序）
| # | 需求编号 | 要求摘要 | 材料现状 | 判定 | 依据原文 |
## 跨域冲突
## 无法判定项及原因（需人工补充的信息）
```

### 7.2 问答输出结构（固定）

```
**结论**：<直接回答>
**依据**：需求 <编号>《<标题>》（语料卷 XX）—— "<原文片段>"
**推断**：<无编号支撑的部分，显式标注>
```

## 9. 构建顺序

存在严格依赖，必须按序：

1. **`build_domain_index.py`**（词边界匹配 + 输出未命中清单）；
2. **盲区清零**（§6.3）—— 补关键词、逐条判归属，直到 135 → 0 或每条均有处置。**此步不通过不得进入下一步**；
3. **生成 11 份 L0 索引 + `_index/meta-rules.md`**，并抽查各域前 50 条；
4. **11 个专家 agent**（彼此独立，可并行编写）；
5. **`SKILL.md` 路由表 + 3 条 `jobs/*.md`**；
6. **`basetech-orchestrator.md`**（需引用已有专家名单）；
7. **验证**（§10）；
8. **Agent 唤醒调用操作手册**（§9.1，交付物）。

先做 1–4 步的**最小闭环**（建议只建 `bt-dtc` + `bt-uds` 两个专家，覆盖约 60% 需求）跑通验证，再铺满 11 个域。

### 9.1 Agent 唤醒调用操作手册（交付物）

Agent 全部创建并验证通过后，产出一份面向使用者的操作手册，**同时写入飞书云文档**（用户身份导入）。

必备内容：

|---|------|------|

## 10. 验证方案

| # | 测试 | 判定标准 | 通过条件 |
|---|------|---------|---------|
| 1 | **路由测试**：每域 1–2 题，共约 20 题 | 编排者派给正确专家 | 路由准确率 ≥ 85%（人工判定） |
| 2 | **防幻觉测试**：10 题中混入 3 题文档未覆盖（如"云端 OTA 差分协议"——文档只管车端） | 专家答"未覆盖" | 3 题全部正确拒答，**零编造编号** |
| 3 | **评审召回**：造一份含 5 处已知偏差的 ECU 设计说明 | 差距清单抓全 5 处 | 召回 5/5 |
| 4 | **生成一致性**：生成 5 条需求 | 复用既有格式与 shall 句式 | 无格式漂移 |

**测试优先于扩写**：先跑通 1–2 个域（建议 `bt-dtc` + `bt-uds`，覆盖 60% 需求），验证架构成立后再铺满 11 个域。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| L0 关键词索引漏召回（**已实测 6.8%**） | 专家定位不到需求 → 错答"未覆盖" | §6.3 零盲区清零作为硬门槛；生成脚本输出未命中清单人工归位 |
| 关键词子串误命中（`can` 命中 `cannot`） | 索引噪声 → 专家被误导 | 词边界匹配 + 各域前 50 条人工抽查 |
| 11 个专家的 `description` 语义重叠 | 路由漂移（派错专家） | 编排者用 `Agent(...)` 白名单约束 + `SKILL.md` 显式路由表；不依赖纯语义匹配 |
| 专家误用 L2 导致上下文膨胀 | 响应慢、成本高 | 正文结构强制「先 L0 → 再 L1 → 最后 L2」，并要求引用最小必要片段 |
| 编排者无法向用户提问 | 信息不足时自行假设 | 编排者必须返回主 Agent 请求澄清（写入其正文的禁止事项） |
| 项目目录启动前提被遗忘 | Agent 静默不生效 | 写入 `SKILL.md` 与项目 README；验证步骤 0 先确认 agent 被加载 |
