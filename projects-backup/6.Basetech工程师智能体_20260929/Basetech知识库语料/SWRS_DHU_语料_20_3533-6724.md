### 3537 — Network management state history buffers
- 版本：v3 ｜ 验证方式：Test ｜ 适用：通用 ｜ Legacy ID：52248v2

To be able to trace state history of NM state machines and added OEM specific functionality. Unified diagnostic services (UDS) - Part 1: Specification and requirements - Data specifies DID, Autosar Network Management (additional requirements) For each network connected to the node there shall be a separate network management state history buffer. Each buffer shall be updated with the last value derived from the respective network management history algorithm. There shall be a time stamp that relates to each value in all history buffers. The source of timestamps shall be a global time received from a master node if available. This enables comparing network historic events across all networks for that node and across nodes. If a timestamp value shall be taken and there is temporarily no communication on the network it is acceptable to use the last received global time. If a global time is not available a local time source can be used, in that case resolution shall be 100ms. If more than one buffer is implemented, the same source shall always be used for all buffers. All history buffers shall operate according to FIFO, first-in-first-out. All history buffers shall hold the 10 most recent states. No changes in states or conditions may be missed. It shall be possible to read each network history buffer by a separate diagnostic identifier (DID). ### 3538 — Storage and clearing of network management state history buffers
- 版本：v4 ｜ 验证方式：Test ｜ 适用：通用 ｜ Legacy ID：52262v3

To be able to correctly trace state history for nodes that support deep sleep. Page No1512(1572) Nodes Type D may not be noticed in advance of release of the control signal IGN, Clamp-15 which often is used to trigger write of data to persistent memory. Therefore this node type shall not be required to persistently store network management history buffer. Nodes Type A, Type B and Type C shall have persistent storage, i. e. in non volatile memory, of network management state history buffers. Persistence is required also at uncontrolled ECU shutdown, e. g. sudden power loss, power supply brown out and unexpected software reset. The state history buffers may be set to the value representing an initial state (Off) and all timestamps be set to the value of 0 at diagnostic reset or at transition from programming session to non-programming session (this is acceptable but not preferred). When exiting sleep mode due to local wake up by a sensor signal change or network activity wake up the state history buffers shall not be cleared to initial state (Off). Node Type D shall at power on, diagnostic reset and transition from programming session to non-programming session, set all positions in all history buffers to the value representing an initial state (Off) and all timestamps shall be set to the value of 0. This node type does not need to have persistent storage of history buffers but it is accepted if it has.

These requirements handle both cases, and there are also specific requirements depending on if the destination network is CAN or FlexRay. Where multi-byte data records are specified and the byte order is not already specified in [Data_4] Global Master Reference Database then the order shall be that the most significant byte of the multi-byte record shall be placed in the data byte with the lowest number according to the data byte numbering convention used in [Data_50] Road vehicles – Diagnostics systems – Diagnostic services. Data type 1- ASCII (American Standard Code for Information Interchange)The ASCII data type contains one character per byte with a value between 0x00 and 0x7F using the standard ASCII code. ASCII parameters shall always be left justified (i. e., the most significant byte represents the first character) with any unused bytes filled with 0x00. Data type 2- BCD (Binary Coded Decimal)The BCD data type contains two numbers per byte with a value between 0 and 9 using the standard 4 bit hex value for each number. BCD parameters shall always be left justified (i. e., the most significant bit represents the first number) with any unused nibbles filled with 0xF. Data type 3- State EncodedThe state encoded data type is used when hexadecimal values represent unique states (e. g., using different values to represent the states of the ignition switch). State encoded parameters shall be limited to a maximum size of 1 byte (i. e., 256 unique states). Data type 4- Bit-MappedThe bit-mapped data type contains the binary state (0/1) of a parameter in a single bit (e. g., the discrete state of an ECU output may be represented as "0" for "Off" and "1" for "On"). If a particular bit-mapped parameter is not supported within a data record that is being reported by the ECU, the value of this bit shall be set to zero. Data type 5- Unsigned NumericThe unsigned numeric data type is used to represent data that has a defined range of values and a specific resolution that can be represented through hexadecimal encoding. Each unsigned numeric parameter consists of a size in bits (n), a resolution (r), and an offset. The minimum value of the unsigned parameter is equal to the offset. The maximum value of the unsigned parameter is equal to ((2 n-1) * r) + offset). The maximum value of n is 32. Data type 6- Signed NumericThe signed numeric data type is used to represent data that has a defined range of values and a specific resolution that can be represented through 2's complement encoding. Each signed numeric parameter consists of a size in bits (n) and a resolution (r). The minimum value of the signed parameter is equal to - (2 (n-1) * r). The maximum value of the signed parameter is equal to ((2 (n-1) - 1) * r). The maximum value of n is 32. Data type 7- Binary floating pointThe binary floating point data type is used to represent data that has a defined range of values and a specific resolution that can be represented through the IEEE 754 single precision standard for binary floating point arithmetic. Each binary floating point parameter consists of a sign bit, exponent, and mantissa that is stored in accordance with single precision IEEE 754. Data type 8 - HexadecimalThe hexadecimal data type contains two characters per byte with a value between 0 and 9 and between A and F using the standard 4 bit hex value for each character. 4.5.2.1.2 Requirements 4.5.2.1.2.1 Requirements from section Diagnostic Data
