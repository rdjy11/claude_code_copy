Qualification method: Analysis, documentation of test results.4.3.7.3.1.4 Protocol over Ethernet Link (4-wire Eth)When the control channel is handled over the Ethernet communication protocol, the communication shall be transparent, thus the endpoint sources and sinks are defining what actualprotocol to use. The default shall however be the suggestion to use UDP for one way traffic and TCP/IP if two way traffic termination is needed. As Control Channel protocol the IP Command Protocol shall be used when Ethernet protocol handles application, diagnostics and SWDL functionality. The LVDS control channel over Ethernet must be able to perform diagnostics over the LVDS link. The methods for diagnostics must be compliant to the [LVDS_Generic:11]UDS Services and [LVDS_GENERIC:13]UDSonIP. Overall requirement of SWDL for private nodes in “General Software Download” [LVDS_GENERIC:5] shall be followed when the LVDS control channel over Ethernet is used. The Internetwork specification [LVDS_APIX_Eth:2] and IP Routing specification [LVDS_APIX_Eth:3] defines a set of rules that must be considered and fulfilled when designing/using the IP Command Protocol [LVDS_APIX_Eth:3] and the control signals used by the applications (which is handled in separate documents). Design Rule: If applications (proprietary) intend to communicate internally within the vehicle network between IP based ECU's and when there is a need of a control channel, this specification (IP Command Protocol) shall be used. The IP Command Protocol specification provides requirements and guidelines how the data shall be exchanged between the ECU's. If the application under development is based on a known protocol (standardized framework), this should be stated in the corresponding IP Signal Content specification (SWRS) and does not need to use the IP Command Protocol). Example the usage of FTP (RFC-959) would mean that this specification is not needed. The Base Tech SWRS includes a set of specification which shall be used together. The IP Command Protocol that contains requirements and design guidelines which must be used for the implementations. The IP Command Bus which defines services which is offered by servers.

It introduces a session layer protocol in the OSI model (see diagram in chapter Overview) for sending and receiving data over. This document will for the most part provide specifications regarding optional features in the DoIP standard. It will also specify hard limits for some "open" values and specify a variety of manufacturer specific values. It will have two Chapters: One for specifying the DoIP requirements for the ECU called "Edge Node". This is the only DoIP ECU in the vehicle. The other Chapter contains requirements for how to handle DoIP communication with the remaining IP ECUs in the vehicle network. The document shall be seen as a companion to the official DoIP specification, giving directions on how we expect the DoIP protocol to behave. This document always has higher precedence over ISO-13400 documents and for conflicting information, this document shall be valid. Anyone who implements the Edge Node, IP ECUs or Tester equipment that shall communicate with these ECUs should read this document. It can also be used as a starting point for testers. The DoIP standard is very open-ended regarding its network design. A vehicle can e. g. expose several DoIP ECUs to the outside world, individually or organized in groups and so forth. The main idea in the vehicle network is to expose a single DoIP ECU and to provide only one IP address to the tester. This makes things like GID synchronization superfluous. The only ECU exposed to a tester is called the Edge Node and all DoIP communication with the vehicle will pass through this ECU. This gives several advantages. With only one point of information flow into the vehicle, one can implement several security mechanisms, which are normally associated with firewalls and intrusion detection systems in "normal" computer network systems. Another advantage with this design is conservation of IP-addresses. There is no ambiguity regarding the mapping between vehicle and IP-addresses. The routing of DoIP messages and diagnostic traffic is also generalized in the Edge Node, e. g. some packets are destined for a Flexray network and some are destined for an internal Ethernet network.
