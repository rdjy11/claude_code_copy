LZSS is a dictionary encoding technique. Unlike Huffman coding, which attempts to reduce the average amount of bits required to represent a symbol, LZSS attempts to replace a string of symbols with a reference to a dictionary location of the same string. The dictionary in LZSS is a sliding window. Compression is achieved by replacing byte arrays found in previously read data with position/length-pairs pointing in to the sliding window. If the position/length-pair takes up more bits than the byte array that it tries to compress, the data is left uncompressed. This is indicated with a single bit flag, '1' indicates that data to follow is uncompressed and '0' indicates that data to follow is a position/length-pair. A flag bit and an uncompressed byte or a position/length-pair are in this document called a compressed data segment. To speed up the compression algorithm a binary search tree is used to store previously compressed data. Appendix: Compression Method #1 Examples, contains C-code examples implementing LZSS compression and decompression.4.6.2.1.4.2 Compression Method #2Software compression is used to minimize the size of the actual data to transmit to in-vehicle ECUs during software download. The compression is performed outside the vehicle before the data is transmitted and the software decompression unpacks the received data in the vehicle ECUs during software download. 4.6.2.1.4.2.1 Data CompressionThe Lempel-Ziv-Markov chain Algorithm (LZMA) is a lossless data compression method, developed by Igor Pavlov. Just as LZSS is a derivative of LZ77, LZMA uses a dictionary sliding window compression algorithm as well but its dictionary size can be much bigger than LZSS, and LZMA also borrows the ideas from Markov chain and range encoding. LZMA stream is encoded to the sequence that consists of matches and literals. For a block of uncompressed data, if there is the same data (a match) in sliding window, then the uncompressed data is represented as a pair of two numbers (distance and length pair). All uncompressed bytes that cannot be encoded as matches are encoded as literals. According to LZMA SDK, the RAM memory required in compression/decompression can be calculated in below formulas: for compression: (dictSize * 11.5 + 6 MB) + state_sizefor decompression: dictSize + state_sizestate_size = (4 + (1.5 << (lc + lp))) KBHere are explanations for parameters in the formulas: dictSize (dictionary size): LZMA SDK recommends the dictionary should be larger than 4 KB, and sets the default value as 16 MB = (1 << 24) bytes. lc (literal context): It assumes how many higher bits of the previous uncompressed byte correlate with the next byte. For example, in typical English text, an upper-case letter is often followed by a lower-case letter, and a lower-case letter is usually followed by another lower-case letter. In the US-ASCII character set, the highest three bits are 010 for upper-case letters and 011 for lower-case letters. When lc is at least 3, the literal coding can take advantage of this property in the uncompressed data. The value range of lc is from 0 to 8. The default value in LZMA SDK is 3. lp (literal position): Sets the number of literal position bits. This affects what kind of alignment in the uncompressed data is assumed when encoding literals. The lp is intended for periodical data when the period is equal to 2^lp. For example, for 32-bit (4 bytes) periodical data you can use lp=2. The range of lp is from 0 to 4. The default value is 0. pb (position bit): Sets the number of position bits. Pb is not in the RAM consumption formulas, but it may affect the size of compressed file. Similar to lp, pb affects what kind of alignment in the uncompressed data is assumed in general. It is also intended for periodical data when period is equal to 2^pb. When the alignment is known, setting the number of position bits accordingly may reduce the compressed file size a little. For example, with text files having one-byte alignment (ASCII, UTF-8), using pb = 0 can improve compression slightly, For UTF-16 text, set pb = 1 is a good choice. The range of pb is from 0 to 4. The default value is 2. Above parameters are saved in LZMA properties (5 bytes, including dictionary size) which is in the beginning of a LZMA data block in compressed file. A delta encoding algorithm takes an old and a new version of a file as input and computes the difference between them. The difference data can then be used to construct the new version of the file by merging it with the old. The measures of interest for delta encoding implementations are the size of the delta and the amount of memory and the time required to construct a delta and to apply it. In order to update an existing software in an ECU by means of delta software delivery, the ECU needs information on how the delta data shall be programmed, E. g. Memory addresses to locate the differences that shall be updated. Also if there are any specific conditions that must be fulfilled before the installation can start, E. g. Software version check, to ensure that the delta is compatible a version number must be provided. This type of “ECU Info” needs to be provided to the ECU somehow and should be included in the delta file during the delta generation process. In addition to delta encoding the Delta Software Delivery Process can also add Software Compression in order to minimize the size of the data that is to be transmitted to the ECUs.
