### 1233 — Forward N_Data from each N_PDU to upper layer
- 版本：v2 ｜ 验证方式：Analysis ｜ 适用：通用 ｜ Legacy ID：128908v1

Decrease the time it takes to perform TransferData via writing frame by frame. The ECU will be able to write the data while receiving new data and thus the ECU will not need to write as much data at the last message and thus the P4 time will be shorter leading to shorter SWDL time. While a diagnosotic server is receiving a segmented request for TransferData 0x36 the transport protocol layer shall send all N_Data from each N_PDU to upper layers that contain the flash programming functions (optional for all other services). If the N_Data is compressed, all N_Data from each N_PDU shall be sent to the layer where decompression is performed, and that layer shall in turn send data as soon as it is decompressed to upper layers that contain the flash programming functions. Note: this contradicts and shall override ISO specified transport layer behaviour which states that the transport layer shall only send complete diagnostic messages to upper layers. Depending on programming alignment constrains of the flash memory, the actual programming of bytes may have to be aligned according to the flash memory and not performed immediately when data bytes are available from transport layer or decompression layer. Example 1: Uncompressed N_Data; a microcontroller has capability to write only 4 bytes at a time into program memory, e. i. not 2 bytes in one event and adjacent 2 bytes in another event. In this case the flash programming function has to reassemble groups of 4 bytes for programming, and must queue any received bytes less than 4 until further bytes are received to get at a group of 4 bytes. In this case 4 bytes of the 6 bytes N_Data from FirstFrame can be programmed immediately, and 2 bytes (6-4) queued and joined with first 2 bytes from the first Consecutive Frame and so on. If the length of the data to be programmed is such that at the end, a group of 4 bytes can not be made, the reaining bytes, less than 4, are written anyway. Example 2: Uncompressed N_Data; a microcontroller has capability to write only 256 bytes at a time time into program memory. In this case the flash programming function has to reassemble groups of 256 bytes for programming, and must queue any received bytes less than 256. In this case FirstFrame + 36 Consecutive Frames (7 bytes N_Data in FF and 252 bytes N_Data in 36 CF: s for a total of 259 bytes) will be received until flash programming can start when the beginning of TransferData request is received, and 3 bytes (259-256) will be queued and reassembled with the following Consecutive Frames until at least 256 new bytes are received. If the length of the data to be programmed is such that at the end, a group of 256 bytes can not be made, the reaining bytes, less than 256, are written anyway. The filter will also make it possible to require a number of correct messages before the received data is regarded as correct. Such a transient filter can be implemented with a counter. If errors are detected in the received data, the counter is incremented and if correct data is received the counter is decremented. The counter has programmable counting factors so that the time until a transient fault is regarded permanent and the time from when the error disappears until it is regarded fault free can be individually adjustable. At a certain level of the error counter the error is regarded permanent and failure management actions are taken. The counting stops at a certain level in order to limit recovery time. When the counter has returned to zero it is assumed that the fault has disappeared. The different limits shall be possible to calibrate from zero to 255. The counting factors shall be possible to calibrate from 1 to 10. It shall be demonstrated that the selected safety mechanisms provide sufficient fault handling capabilities for the considered network. The recommendations in this guideline are based on the recommendations in [SafeCom_1] for communication using E2E that are developed by safety experts within AUTOSAR for up to ASIL D communication. These recommendations shall be confirmed to be appropriate in the Item, fulfilling the Item's own safety requirements and any external safety requirements. These safety requirements include ISO 26262 requirements on hardware architectural metrics and requirements for safety goal violation rates. It should be noted that the recommended safety mechanisms in this guideline are safety mechanisms in addition to the safety mechanisms already implemented in the communication bus used. These additional safety mechanisms are intended to protect against faults occurring in the communication stack and also to enhance protection against faults occurring on the communication bus itself. Depending on application and the ASIL of the relevant failure modes, the safety mechanisms in the communication bus may be sufficient.4.3.11.1.9.2 Relevance of This Guideline When Developing a Technical Safety ConceptIn order to achieve safe communication, the complete communication chain between the sender and related receivers shall be considered, including the communication bus and COM BSW. It is a packet oriented system with mechanisms for flow control, data integrity and many other features. Practically every modern customer-grade PC contains software for communicating over TCP/IP which makes it ideal for interfacing between a very open-ended user machine and vehicle. UDP is the sister protocol to TCP and is necessary for smooth integration with an Internet-like environment. One may have TCP without UDP or even IP, or any combination but for communication with PC: s they are all needed and should be implemented together in a bundle. The bundle of the Internet Protocol Suite and all other protocols and algorithms for communicating over the Internet is sometimes referred to as "Internetworks", hence the title of this document. The Internet Protocol suite will most likely be implemented in-vehicle as a result of a series of various factors, such as: law requirements regarding vehicle diagnosis, demands for higher bandwidth due to growth in ECU software and not least connectivity with customer applications. There are many TCP/IP stacks available with various licenses and openness ranging from the very permissive to closed. In short, there is an abundance of mature available implementations that can, and should, be used. This document will sometimes mention the underlying physical layers, but most of the requirements in this document should be considered generally valid for most high-speed physical layers with some modifications. Requirements for bandwidth / throughput are NOT specified by this document, but will rather be defined by either the physical layer specification and / or the application layer specification. The Open System Interconnection Reference Model (OSI Reference Model or OSI Model) is an abstract description for layered communications and computer network protocol design. The Internet Protocol Suite defines only the Network (IP) and Transport Layer (TCP/UDP). This is accomplished by informing Local Software Components, LSC (within an ECU) and software components running on other ECU's when services are available. The basic principle is that one LM module instance will be running on each vehicle internal IP ECU and that these distributed LM instances shall be communicating with each other using IP Command Protocol, while LSCs only communicate with their ECU local LM instance as shown in figure [IP Link Manager – Overview of the communications path shown by the arrows. The green arrow is an IP based communications link while the gray arrows represent local SW interfaces]. When an ECU is initialized, the local LM module starts to periodically broadcast that all services configured to start on the ECU, are available to other LM modules. When the LM module is initialized it will discover possible existence of external LM modules that also are broadcasting their existence throughout the vehicle internal IP network. In that way, each LM module will know availability of all other LM modules. Services are distributed throughout the vehicle network, so the IP ECUs are assigned members of groups referred to as Resource Groups, RG that each encapsulates a set of services that are provided by them. An LSC may need a service, in which case it can request the local LM module to make the service available by starting the Resource Group that provides the services. If the Resource Group is already enabled it may be kept available for the duration on the LCS process. There is no mechanism for requesting one specific service, so requesting a Resource Group will enable all provided services. If the local LM module detects not all expected LM instances are available, the local LM instance tries to enable them by sending a “vehicle bus ECU wakeup” system signal on the vehicle bus. The exact name of the “vehicle bus ECU wakeup” system signal is ECU dependent and therefore not described in this document. These are described in [SRD : Infotainment Platform]. LSCs may also request services with high priority, in which case the local LM instance adds this information to its broadcasted Request messages. The external LM modules then realize that the received Request messages has high priority thus ignores normal power handling, until the high priority request is no longer received.
