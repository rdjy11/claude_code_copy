### 3377 — TransferData Service
- 版本：v1 ｜ 验证方式：Test ｜ 适用：通用 ｜ Legacy ID：341553v0

There is an requirement to support the complete vehicle to be re-programmed via a CAN interface. Since the maximum message length on a CAN based network is limited to 4 kB the diagnostic tester needs to reduce the message length if an ECU(server) is responding with a maxNumberOfBlockLenght larger than the transport protocol is supporting. The TransferData message length of 3842 bytes (0F02 hex) shall be supported independent if the parameter maxNumberOfBlockLenght returned in the RequestDownload service is larger,Note 1: The Diagnostic tester is normally using an interface towards the vehicle supporting message length larger than 4 kB, therefore it is required to support as large block lengths as possible to reduce the software download time. Note 2: The 3842 bytes is calculated from the formula (n*256) + 2 bytes, where n=15 and the 2 byte will take the SID and block sequence counter.

It applies to CAN and FlexRay networks. Component contextThis SWRS describes Network Management for Autosar based nodes. Network management within Autosar is limited compared to the desired network management functionality. The basic scope of Autosar network management is to coordinate the network requests of all or some nodes on a single network in order to obtain a controlled, simultaneous and synchronized shutdown of communication when those nodes are ready to go to sleep. With partial networking (PNC) the scope applies to multiple networks. The scope of network management desired is more extensive and is described in this document. It includes: Start-up timing of communication on a node by network wake up, hardware wake up and power on (i. e. also relates to hardware performance). Support of network communication state history for diagnostic purposes. The ECU specific decision when to request a network to be active or not active is not defined in this document. However network management is a mechanism and protocol where NM-PDUs are sent between nodes for communicating the needs for network communication. Communication needs may be defined elsewhere and determined on logical level (in application SW-Cs) by Virtual Function Cluster (VFC) activation and deactivation criteras. If BSW supports partial networking, then VFC requests are translated in BSW to Partial Network Clusters (PNC) requests which are communicated among nodes in NM-PDUs. PNCs are related to physical networks being requested active or not active. Partial networking may improve energy efficiency by only activating currently needed networks and nodes. In this specification, timing requirements for a node are only applicable when network communication has been granted to be activated, the specific communication conditions is expected to be found in node specific requirements. Other generic requirements applicable when implementing logic for requesting communication can be found in Autosar - ECU Mode Management. FlexRay schedule coordination is described in FlexRay Data Link Layer.
