### 355 — CC Subscriber ECU configuration states
- 版本：v7 ｜ 验证方式：Test ｜ 适用：通用 ｜ Legacy ID：65555v6

To define the possible states (including necessary handling) of CC Subscriber ECU configuration using allowed CCP data. a) CC legacy general principles: The ECU/system shall determine what appropriate action(s) are to be taken for a specific function/feature when utilizing a default configuration or validated CCP data. The ECU/system failure mode handling/operating strategy might contain additional routines that need to be handled and documented. CC Subscriber ECUs shall implement default values for CCPs based on any required default operating condition so that the appropriate functionality can be achieved and where necessary failure mode management actions shall be active. The default operating conditions are dependent on the strategic requirements of the ECU. The operation of the functions within the ECU strategy shall be in line with FMEA rules affecting safety of the vehicle and occupants and customer satisfaction in the absence of configuration information. Wherever possible the vehicle should operate normally. If the vehicle could be made dangerous or perform unsatisfactory for the customer/occupant, then failure mode management actions need to be executed to prevent or change this vehicle behaviour. The failure mode management actions shall be in respect of the ECU FMEA recommended actions. b) Two CC Subscriber ECU states are defined as follows: Bulk State: In this state to receive required Car Config parameters for the first time and keep state until all have been evaluated valid: The below applies to every CCP that the subscriber ECU expects to receive and evaluate: Whenever a valid CCP value is available/received it shall be used. For a received but not valid CCP value, use the ECU default value for that parameter instead. Valid Configuration State: In this state only to detect a possible change in car config parameter values: The below applies to every CCP that the subscriber ECU expects to receive and evaluate: For a received but not valid CCP value, consider using the previously stored valid value for that parameter instead. CC Subscriber state guidelines provided for configuration using CCP data (distributed within the VCP signal) in chapter Guideline subscriber states. c) Evaluation of a CCP value implies that (compared to whatever configuration the ECU/system currently utilizes) the ECU/system must determine if a received CCP value is valid, e. g. recognized, within valid range for acceptance, possible to transition to if ECU already has a Valid Configuration State etc.

### 358 — Invalid or unrecognized parameter values
- 版本：v7 ｜ 验证方式：Test ｜ 适用：通用 ｜ Legacy ID：65582v6

To prevent any damage/security risk internally/externally in the CC Subscriber ECU associated with invalid or unrecognized parameter values. If any CCP value(s) used for configuration (including values $00_H$ and $FF_H$ ) is received and evaluated invalid or unrecognized by the CC Subscriber ECU, the related function shall perform the following actions: a) Enter a safe mode (depending on ECU strategy in line with FMEA rules) if there is an imminent risk of serious errors. b) Use DTC "Car Configuration –Invalid/Incompatible Configuration" U2300-56, DTC test according to [CCF_2] UDS Data. c) Minimize (avoid if possible) the impact on functions not related to parameter usage. Note: For functions that are not safety nor security critical, whose behaviour/setting would be a similar or equal even if a received CCP value is not expected, a range of CCP values could be adopted as valid, e. g. CCP value range 0x01 to 0xFE is valid for configuration.

- 版本：v7 ｜ 验证方式：Test ｜ 适用：通用 ｜ Legacy ID：65583v6

There are two major types of configuration methods: Global and Local. Configuration parameters, often compiled within a SW file that may contain only one of those two distinct parameter types. Local parameters may either reside in a separate file or can be embedded in ECU's software. Properties for SW Configuration files: Handled according to approved SW handling processes. Traceable in individual car. Downloaded at assembly plants or service shops. Stored in SW databases. Page No101(1572) 4.1.2.1.1.1 Configuration Using Global ParametersGlobal parameters denote major systems, functions and features implemented in vehicle via ECU applications. Global parameters notion is often termed Central Car Configuration (or CarConfig in short), are used to configure ECU functions centrally over a distributed network during run-time. The CarConfig file is generated when the vehicle is built or updated; therefore it is unique per vehicle. Parameter values are stored in the Central Electronics Module or equivalent, from where they are transmitted on all networks to the ECUs requiring them. It is strongly recommended to choose each parameter as specific and function oriented as possible. This facilitates to reconfigure multiple ECUs just by generating & downloading new CarConfig file. In general following guidelines should be fulfilled when applying global parameters changes: Each parameter value shall specifically point out the behaviour of the function using that parameter. A parameter with an indirect effect on the functional behaviour (e. g. market code or date) shall not be used, for two reasons: If the relationship between the indirect parameter and the functional requirements is changed (e. g. the legislation on the market is changed) the function will no longer behave correctly. If a new code for the indirect parameter is introduced (e. g. new market) the new parameter code cannot be used to configure the function without re-writing the software in the receiving ECU. It shall not be possible to add an accessory function by only altering a parameter value. Adding an accessory function (e. g. cruise control) must involve the download of additional software (i. e. a new software part number). A global parameter should not be unique to a specific ECU; i. e. other ECUs would preferably be able to use it. Thus it gets usage potential by multiple modules/features as desired by CarConfig notion; otherwise this should be solved locally. It's not allowed to re-define (name & content of) existing parameter values, if they have already been used in customer cars. A global Parameter can not be dynamic relying on a network signal from another module as to calculate the parameter value to be published over the network. The parameter would rather be generic and not for a specific platform usage solely, to facilitate carry over/back of nodes & functions. This mechanism can be used by subscribers to mitigate customer symptoms and/or improve the ability to diagnose and rectify the vehicle. This guide line defines a method for publishers to define a Quality Factor, and subscribers to reacts to it to ensure that the QF provides the intended benefits. 4.3.5.1.1.2 RisksIn the past, misunderstanding and therefore inappropriate use of this and similar mechanisms has sometimes had the opposite effect i. e. it has aggravated symptoms and made it harder to diagnose and rectify the vehicle with in some cases some severe costs as a consequence of the errenous hanling. Therefore it is of absolute importance that all affected participants agree upon and document when and how to behave on the different levels of quality factor values. There have been many problems caused by the functions in publishing ECUs calculating QFs wrongly and the functions in subscribing ECUs reacting wrongly to QFs even where they have been calculated correctly. It is vital therefore that designers of subscribing functions carefully check the behaviour of the publishing function and do NOT rely on them meeting this guide line. The level of accuracy or tolerances of a signal value is not of interest in this document and must be documented in another document, see section Who should read this document?.4.3.5.1.1.3 Who should read this documentThis document should be read by the system integrators, the component developers, the test engineers, and the function owners which are using or will use quality factor signals. They together must agree upon a strategy how to handle different levels of quality factor values and manually document it properly in the SWRS so all future users (senders and receivers) of a quality factor signal always know how a certain quality factor value must be treated.4.3.5.1.1.4 Definitions and Abbreviations Definition/Abbreviation Description ECU Electronic Control Unit DTC Diagnostic Trouble Code ERC Emission Related Component, FMEA Failure Modes and effects analysis NOS Network Operating Software. The standard software package which includes a component to handle network communications. Operating Cycle The Operating Cycle consists of the time between Power Up (alt. Wake Up) and Power Down (alt. Enter Sleep Mode) as specified by each node specification. To be able to inform the node using the data about the data quality, a 'quality factor' value (Q-factor) can be linked to the signal containing the data and sent over the network at the same time. The 'quality factor' indicates some status information about the data signal, e. g. if the value is inaccurate because of a faulty sensor, and can be used to make decision about replacement values/reconfiguration. 4.3.5.1.2.1 QF values definition and use4.3.5.1.2.1.1 Value 3 - 11b OKThis value indicates that the signal is accurate and that the data it contains is truly representative of the real state. The accuracy of the transmitted signal under this normal operating condition should be stated in the signal definition in the SWRS.4.3.5.1.2.1.2 Value 2 - 10b Not within specificationThis value indicates that although the signal still contains data that is representative of the real state of the vehicle, a fault has been detected which indicates that the accuracy has been affected to an extent which may affect the performance or durability of exceptional subscribers. Which nodes that are typical subscribers, exceptional subscribers and the tolerance for the value 2 must be agreed in advance and the expected behaviour of subscribers must be well known and documented. The reduction in accuracy from that achieved with normal operation must be well documented. It is expected that only a small minority of subscribers to QFs will react to the value 2. Example: Engine torque calculation - if the primary input of mass air flow fails it is possible to determine engine torque using manifold pressure, but with a notable reduction in accuracy. Most users of the Torque signal will not be affected but the reduced accuracy may not be adequate to allow the optimum shift quality / durability compromise to be maintained in the transmission. In this case the transmission can change to a slightly jerkier, but still functional, shift behaviour with minimal effect on the customer4.3.5.1.2.1.3 Value 1 - 01b No data existsThis value indicates that the signal is set to its initial value because it has not yet been possible to measure or calculate real data. This situation may persist until the node power up sequence is fully completed (all applications have been executed at least once). The expected delay until real data is provided should be specified by the publishing node and/or function owner. The QF must change to a new appropriate value as soon as the application program has started to write fully valid information (this means that the real measurements and/or calculations are complete and enough time has elapsed for any filter function to have a valid output value) to the NOS. The receiving function must be designed to function correctly with no data for up to the maximum time defined above. After this time it should treat a QF value of 1 as identically equal to a QF value of 3 unless there is a clear and documented customer benefit for it to do otherwise. (This is to support legacy and minimise the customer impact)There must be no undocumented assumptions or interpretations of the QF! Example: receiving functions should not assume that they will always receive the value of 1 and should NOT attempt to use it as a reset marker. Some transmitting functions may be able to transmit valid data fast enough to catch the first transmission by the NOS. If there is a need for a more extensive information exchange for a specific feature, then this must be solved with a unique defined signal between the concerned functions, and shall not be solved by a undocumented interpretation of the standard QF.4.3.5.1.2.1.4 Value 0 - 00b FaultyThis value indicates that there is a serious fault which prevents the signal being correctly generated by the publisher. The publisher may store a DTC to indicate this. Where there is ANY useful data potentially left in the signal under these conditions, this should be stated in the SWRS to allow subscribers to make an optimum judgement as to whether customer functionality can be preserved. Subscribers which can no longer provide safe and/or reliable customer function must default to a safe condition and if required store a DTC indicating what has happened. Note, as with the publisher, the subscriber must give careful consideration to whether it is actually necessary to remove customer function, particularly when the received signal is a secondary input to the function. It is not generally recommended that subscribers use the data when QF = 0 and extra care should be taken if the option is used.4.3.5.1.2.2 QF values definition and use summary tableThe following table summarises the specified behaviour of publishers and subscribers, but it is essential that the detailed definitions above are studied in addition. The basic question is "what if a disturbance of typically short duration occurs such as a voltage spike?". In this case the publisher may be temporarily unable to provide accurate data. If it is determined that the module must report a problem with the data due to low or high supply voltage, an appropriate QF value must be chosen depending on the accuracy of the data as for any other fault.4.3.5.1.2.3.3 Engine crankingA very important special case of a temporary inability to transmit correct data is during engine cranking, or more generally during changes of vehicle power states. There is a generally agreed principle that ECUs should detect cranking, and not react to problems of any sort, including unexpected QF values, or set DTCs until a suitable time has elapsed after the engine has started to be sure that full function of the electrical system has been restored. Of course the exception to this is ECU functions which are needed to enable the cranking process. Unfortunately there is not yet an agreed standard for all brands and vehicles as to how this should work and it also depends on the vehicle architecture.4.3.5.1.2.3.4 Detecting missing dataThe QF is just like any other signal as far as its transmission around the network is concerned. It is NOT modified in any way by passing through a gateway, nor changed if missing frames are detected. Other mechanisms exist to deal with these issues, and QFs should NOT be used for this purpose. The QF shall not and can not be used by the subscriber, to get information on whether or not the publisher function is reporting any data to the network transport layer. This shall be taken care of by an UB (UpdateBit) or other mechanism such as a message counter.4.3.5.1.2.3.5 Multiple variants of a nodeIn case different variants of one node exist (e. g. Engine Control Modules, Brake Control Modules...), these nodes shall ensure that they apply the same rules for generating QFs they send out across their variants. In this case, the receiver can always react in the same way on a specific QF signal received from different node variants, i. e. has a common interface to the variants. 4.3.5.1.2.3.6 Data valueThe corresponding data signal to the QF signal shall always contain the actual measured/calculated value for the transmitted data. This is valid for all possible QF values. Only during initialization, this data signal may contain the init value defined in the signal SWRS.4.3.5.1.2.3.7 Philosophy and development of the QF conceptThis section is not formally part of the definition, but attempts to explain the logic for WHY the guideline has been written as it has, and the history of problems which have lead to this logic. It is vital to understand that the QF is a mechanism to assist the mitigation of faults for the benefit of the vehicle user only. It only has meaning as part of the design of a distributed function in which sharing of data contributes to delivering a customer feature. In the past the generation and use of quality factors have been done in isolation which has lead to publishing nodes setting low quality factor values too readily, and subscribing nodes having needlessly severe reactions. This combination produces a situation where the symptoms experienced by the customer in the vehicle may be far more severe than is actually justified by the fault which has occurred. The QF guideline can't cover all possible needs of data quality information, but is rather a generalized standard method that will fit the majority of needs. If there are exceptions that can't be handled within the framework defined in this spec, then the subscriber and publisher must agree upon a specific solution for their specific need. It is essential that each user of a QF checks that their reaction is appropriate to the behaviour of the publisher. It is expected that the FMEA of the function should indicate the effect on that function of an error in its incoming signals. This should inform whether a QF is needed at all, and what the correct reaction should be. In theory of course it may be that different users of a signal might have different accuracy thresholds where reactions were required. For this reason there may be cases where quality indication mechanisms not covered by this framework are needed. This spec does not forbid these. So far no case has been found where defining more than two different states of degradation produce additional benefit.4.3.5.1.2.3.8 History of QF 1The QF value of 1 requires some specific explanation, as it has caused confusion and debate in the past. This value was used in earlier versions of this specification as the initial value AND to indicate that although no fault had been detected, some diagnostic evaluation was still ongoing. The classic example of this is the coolant temperature. OBD legislation requires that this is monitored to make sure the engine is genuinely warming up correctly. This evaluation inevitably takes many minutes, and there may indeed be usage patterns of the vehicle where the evaluation is never completed. There is no conceivable customer function on the vehicle which could not operate for several minutes after start, and in some usage patterns not operate at all. Therefore there was no useful way in which a subscriber could react in any other way to the value of 1 than to treat it exactly the same as 3. Unfortunately many subscribers followed a wrong but understandable logic that because 2 was worse than 3 and 0 was worse than 2; then 1 must also be worse than 2. This created fundamentally wrong behaviour in the vehicle which required software changes to correct it. The definition of QF 1 now should eliminate this doubt, but subscribing functions should be designed where possible to work correctly with publishing functions with the earlier behaviour to avoid the cost and risk of changing the publishing function. If there is a need for a more extensive information exchange for a specific feature, then this must be solved with a unique defined signal between the concerned functions, and shall not be solved by a undocumented use of the standard QF. An example of this has been raised in the late stages of development of this version of the specification. This occurs in vehicles where the steering angle sensor can only detect movement of the steering wheel and not its absolute position. An absolute position is established by learning the straight ahead position by correlating with wheel speeds and yaw rate. This takes some time and clearly can only happen with the vehicle moving. The straight ahead position is remembered when the power is off, but if the steering wheel is moved with power off, there will be an error until a new straight ahead position is learned. None of the defined QF values in this spec allow for this, so a further signal indicating completion of the learning process had to be added to the vehicle4.3.5.1.2.4 Recommendations for creation of QF: sThe Quality Factor (QF) should handle and carry the quality number (value) of the data transmitted on the vehicle network.
