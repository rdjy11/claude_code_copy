### 492 — Network event - wake up request to slave ready to communicate
- 版本：v2 ｜ 验证方式：Test ｜ 适用：通用 ｜ Legacy ID：53602v1

The LIN slave node shall detect the wake up request and be able to transmit valid data within 100ms. Slaves shall not respond until their data is valid. Diagnostic supervision in the master shall take this delay into account. Specific subsystems that require a faster wakeup response time can be defined in the subsystem application requirements.

The GMSL2 chipset interleave a half-duplex control channel together with the high-speed video stream sent from the video source to the video sink (see figure LINoverLVDS on GMSL2 Link Concept overview). The control channel can be used both for reading registers in the GMSL2 chipset and communication between the MCUs integrated in the ECUs. The control channel requires a higher-level protocol implementation in order to avoid collisions on the link etc. which is described in this specification. This is further described in Section: LINoverLVDS on GMSL2 protocol. The LINoverLVDS on GMSL2 is based on LIN, but has a different characteristic. Hence, the LIN specification is applicable as long as this specification does not specify otherwise. This is further described in Section: LIN inheritance for LINoverLVDS. The LINoverLVDS on GMSL2 datalink layer needs to be implemented as a part of the ECU Software. The GMSL2 physical interface needs low level drivers in combination with higher level functionality to make full use of the built-in functionality of the GMSL2 chipset (e. g. settings for equalization, pre-emphasis, video format etc.). The protocol is a point-to-point network and defines one diagnostic master, and one diagnostic slave. The diagnostic master is the ECU in charge of the communication on the control channel. The diagnostic slave will only communicate on the control channel when data is requested by the diagnostic master. This is further described in Section: Diagnostic master and diagnostic slave. The LVDS is a high performance data transfer application for today’s new technology. This technology is based on ANSI/TIA/EIA-644 LVDS interface standard. The LVDS technology with a low-voltage differential signal (up to ±800mV; typically ±250mV to ±450mV for the variants based on the mentioned standard) and fast transition time, allows products to reach from 100 Mbps to over 2.5 Gbps of data rate. In addition, the low-voltage swing reduces power dissipation, along with the advantages of differential transmission, i. e. lower electromagnetic interference (EMI). The LVDS technology could be applied for simple line driver and receiver physical layer interface devices and more complex communication chipsets (serializer and deserializer). The LVDS technology can be used over distances ranging from a few centimeters to 10 meters. Today more and more displays are being fitted into vehicles, including the electronic panel that presents speed, revolutions per minute, vehicle status, etc., and multimedia displays for the rear passengers, who can then watch TV or DVDs. Each display requires a video transmission link. Future vehicles may include various cameras to assist the driver, such as cameras for the Page No394(1572) rear-view mirror and wing mirror as well as night-vision cameras. Each camera requires its own video transmission link routed to the display. The number of transmission links in the vehicle is thus growing, which is presenting more and more problems in the transmission of analog signals due to electromagnetic interference. By using LVDS links, video interference is thus minimized. The LVDS network layer software need to be an integrated part of the ECU SW. The LVDS physical interface needs low level drivers, as well as higher level of functional usage of the built in setup and test functions of the LVDS link concept. However to make it possible to upload parameters related to the adoption to the actual used length of the cable connection between the ECUs, upon the LVDS link function is implemented on, the parameter sets must be both possible to tune and optimize but also it must be possible to store the correct settings per LVDS link. As an ECU can have multiple LVDS links, both composed upon one-wire implementation, two-wire implementation and four-wire implementation, the settings need to be specific per ECU type, wire length and LVDS link interface. Care should be taken, not only for the local ECU settings for LVDS link side, but also for remote side LVDS settings – parameter settings in the ECU on the other side of the LVDS link, this is due to the overall LVDS link transfer function characteristics – the LVDS link concept will be defined by Serializer, Tx, side settings, cable length/characteristics and the Deserializer, Rx, side settings. Each communication link can handle several video streams simultaneously with multiplexing technology, if required. The main function of the LVDS nodes is to distribute video streams from a source to a sink. Depending on the LVDS sources, the nodes can also transform a video stream from one type to another to adopt the image characteristics. Typical transformations can be selection of one two (or more) video stream from the source, into different LVDS destinations. Other transformations can be resize, reshape or resample the incoming LVDS video into the outgoing LVDS video stream. In case the incoming LVDS video is coded, block coded or simply YCrCb (422/420), the node can transform this into more display friendly video streams, like RGB (444) or YCrCb (444). All transformations of the video streams can add latency – please refer to system level requirements in this specification.
