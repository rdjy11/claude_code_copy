### 1512 — Seamless Roaming
- 版本：v10 ｜ 验证方式：Test ｜ 适用：通用 ｜ Legacy ID：57802v9

To ensure that Seamless roaming with in ESS is supported when connected to Access Points. Scenario B in WLAN Security, doc [31836301]. WLAN Security, doc [31836301]. Document typeNote-SWRS Page No638(1572) The WLAN transceiver shall support roaming within ESS when connected to OEM Access Points. Application shall support two methods to perform roaming (default shall be configurable via Local Config File REQPROD 242995). Used roaming technique may make an impact on the traffic while scanning and therefore it's recommended that the WLAN transceiver only performs scanning while not actively transmitting data. SignalStrengthRoamingAfter a successful connection, start measuring the RSSI (Receive signal strength indicator) on the link. If, the RSSI is less than the SignalStrengthThreshold, start scanning for neighbouring AP's for time SignalStrengthTime. If better neighbouring AP's are identified which matches SignalStrengthHysteris (parameter according to REQPROD 242995) the WLAN transceiver shall initiate re-association with AP. BackgroundScanningRoamingWhile connected, the WLAN transceiver may scan for available channels before roaming shall be performed. The application shall constantly build-up knowledge of the RF environment and AP in ESS. Scanning shall be performed according to RoamingType parameter defined in REQPROD 242995. It's required that the supplier consults with the OEM to use the best possible roaming technique and roaming performance values to cover Scenario B according to reference. Note: For tuning activity, it's important that the above mentioned parameters (REQPROD 242995) are configurable within the local config file which defines the default start-up behaviour.4.3.18.1.2.4.3.2 ScanningBefore using any network, stations first need to find it. A mechanism to find available networks Page No639(1572) (BSSs) in the radio vicinity is called Scanning. IEEE 802.11 standard defines two methods for scanning. Passive scanningActive scanningPassive Scanning: Passive scanning saves battery, as it does not require transmission from scanning station. In Passive scanning mechanism, STA moves to each channel in channel list and waits for Beacon frames for configured period of time. Beacon frames from all discovered networks on channels in channel list, are buffered and presented to layer above in Scan Report. During passive scan, the device does not emit any RF power. Active Scanning: Active scanning takes more assertive role compared to Passive scanning. Instead of waiting for Beacon management frames on each channel in Channel list, Active scanning STA sends a Probe Request frame after probe delay on each channel and waits for Probe response frames from networks active on that channel. Active scanning can be used as either directed Probe Request (to a known SSID) or as a broadcast Probe Request. Probe Request frames sent by scanning STA are subject to DCF access procedures. Some countries put regulatory restrictions on use of Active scanning while operating in certain frequency band or on certain channel in frequency band. As per the reference specification, WLAN Security Requirement Specification, Document nr: 31836313; vehicle projects using Wi-Fi as STA shall avoid using Active Scanning. Note: In both type of Scanning, it is possible to specify filters to narrow the search criteria. Additionally, the number of channels to scan depends on which frequency band the WLAN transceiver are allowed to use for the specific region/country. The parameter Country Code has been defined in REQPROD 97421 Local Configuration Data, which shall be used to set the specific region/country which the vehicle is sold to. Note: It cannot be assumed that all vehicles in the fleet has telematics and/or GNSS which allows the vehicle to identify which country/region they operate in. The intention with the scan parameter settings in Local Config File, is to be able to switch scan behavior without the need for re-compilation of source-code. Example: During development/tuning phase it's identified that the passive scanning is to slow to identify APs or the scan downgrades the throughput performance too much. In such scenarios, it shall be possible to switch to Active Scanning as default behavior by using settings in Loal Config File. When ECU boots, the application reads the local config parameters and sets the default scanning behavior. Infrastructure BSSIn Infrastructure BSS, stations cannot communicate to each other directly (unless IEEE 802.11z is supported) and have to go through access point. This also means that communicating devices do not need be in direct range of each other. They just need to be in communication range of access point increasing communication range of basic service set (BSS). As all communication is relayed through access point, it takes more transmission capacity when compared to Independent BSS but it also reduces complexity of PHY layer as STA are not required to keep database of neighbouring STAs relationships within basic service set (BSS). Also, access point is in better position to assist STAs who want to save power by monitoring their state and buffering frames for STAs while STAs are in power save mode. Independent BSSIn Independent BSS, devices/stations can communicate to each other directly and hence needs to be in communication range of each other. Typically independent BSS are set up temporarily and teared down when purpose is accomplished. So generally Independent BSS are short lived. Independent BSS are also called Ad-hoc BSS or Ad-hoc network. Extended Service SetIEEE802.11 standard provides a way to link multiple BSSs to form a larger Extended Service Set (ESS). ESS is generally created by linking multiple BSSs to a backbone network. All linked BSSs in ESS share same SSID i. e. network name. STAs which are on same ESS can communicate to each other using backbone network (Distribution system). A large ESS enables the possibility for STAs to no be confined to a smaller coverage area of single BSS and roam free within ESS without losing connectivity to network. 4.3.18.1.2.8.1 ESS

At least this would cause a serious performance hit to the system because of the CSMA/CA technique used in IEEE 802.11 networks. The impact of this attack could be reduced by changing the AP channel, however this will probably cause synchronization issues between ECU and AP, furthermore the attacker can also change channel.4.3.18.3.1.2 DoS Attack 2A second DoS attack is possible by injecting forged management frames on the network (these frames are always sent unprotected on the network), e. g. deauthentication or disassociation frames. This is possible by injecting a packet that seems to originate from the AP (by using the APs MAC-address as sender address in the MAC-header) which will force the ECU to reauthenticate or reassociate.4.3.18.3.1.3 DoS Attack 3 - Memory Exhaustion AttackBecause the first message of the 4-way handshake is not authenticated (this is before PTK generation) it is open for spoof attacks. The ECU has to store all received messages 1s and the generated PTK associated with it until positive confirmation from the AP in message 3. An attacker could continuously generate false message 1s in the 4-way handshake process, potentially causing memory exhaustion in the ECU.4.3.18.3.1.4 Evil Twin AttackIt is possible to set up another AP with the same SSID as the real network, tricking ECUs to connect to the rogue AP instead of the real one. Combined with a fake AS this could be a serious security threat. To fight this type of attack or at least reduce its impact, it is imperative that the ECU only exchange information with an AS that present a known and valid certificate. By just tricking ECUs to connect to a rogue AP however the attacker has successfully launched a type of DoS attack effectively stopping ECUs from accessing the real network.4.3.18.3.1.4.1 Rogue APEven with the chosen RSN architecture using EAP-TLS an attacker can set up a fake AP, which mirrors the SSID, encryption type and band. It's possible for the attacker to configure the fake AP to capture and record all authentication requests. The attacker then waits for the user to attach to the fake network and captures their credentials and it's possible that the attacker may crack the challenge/response pair to recover the password.4.3.18.3.1.5 Other AttacksSeveral other attacks are possible for pre-RSNA algorithms such as WEP or the less secure RSNA-PSK (WPA-PSK/TKIP/RC4) mode. As the use of these methods are prohibited according to this specification, the potential attacks are not further investigated here. 4.3.18.3.1.6 Packet modification attacksThe integrity protection of EAP-TLS packets does not extend to the EAP header fields (Code, Identifier, and Length) or the Type or Flags fields. As a result, these fields can be modified by an attacker. In most cases, modification of the Code or Identifier fields will only result in a denial-of-service attack. However, an attacker can add additional data to an EAP-TLS packet so as to cause it to be longer than implied by the Length field. This documentspecifies security requirements both on the ECU containing the WLAN interface as well as on the access point that the vehicle shall be able to connect to. The document is intended for the developers of the component that provide a WLAN link between the vehicle and networks outside of the vehicle. That includes networks at manufacturing sites, service and aftermarket sites and PD development sites. The developer may be an external supplier or an internal software department. The document is also intended for tool vendors that will provide equipment that will be used at manufacturing sites, at service and aftermarket sites and during internal development within PD to diagnosis and download software to ECUs within the vehicle. The third group that this document is intended for are those within cars that are providing it-infrastructure to manufacturing sites, service and aftermarket sites, and PD. If the software product is a part of a larger system and interacts with other software products, this document also should be read and approved by the system designers and the designers responsible for each interacting software product. IEEE Std 802.11i-2004 (amendment to IEEE Std 802.11-1999) introduced a new security architecture named Robust Security Network (RSN). This amendment relies on IEEE Std 802.1X-2004 and was issued to remedy security concerns regarding wireless connections as detailed in IEEE Std 802.11-1999. That particular standard relies on WEP for confidentiality purposes, a now deprecated pre-RSN algorithm which can be cracked in a matter of minutes using widely available tools. IEEE Std 802.11i-2004 is now a part of the updated IEEE Std 802.11-2007 which is the current standard for WLAN communication and the basis for this specification. The standard specifies the PHY and MAC layer according to the OSI model. The security aspects detailed for the ECU in this document is relevant for the MAC layer and does not rely on a specific PHY layer. Certain communication protocol discussed for other entities in this documents are implemented in higher layers e. g. AP-to-AS communication. All commercially available WLAN-equipment is normally certified by the Wi-Fi Alliance. The commercial name for a full implementation of IEEE Std 802.11i-2004 is called WPA2 Personal (PSK) or WPA2 Enterprise (IEEE Std 802.1X-2004 authentication). All equipment carrying Wi-Fi certification sold after 2006 have to support at least WPA2 personal. The purpose of this document is to define how the RSN architecture should be used to reach a comparable level of confidentiality on a wireless link as to a wired connection. Furthermore, this document intends to support various VCC scenarios where one WLAN transceiver (in the vehicle) will be used for two scenarios with different purpose (Access Point or Station). Extra care has to be taken, since the internal WLAN transceiver shall cover two security strategies (methods). The ECU utilizes the same algorithm and compares its calculated three byte key to the key submitted by the tester to determine if security access is granted or not. The algorithm described in this document generates a three byte response (key) to an eight byte challenge. The eight byte challenge consists of three random seed bytes (S1, S2, S3) and five fixed bytes (F1, F2, F3, F4, F5). Note that the five fixed bytes are not transmitted on the network and must be known in advance by both the ECU and tester. These fixed bytes are also referred to as the Security Constant. The seed bytes are transmitted from S1 (most significant byte of the 3 byte seed) to S3 (least significant byte of the 3 byte seed) in a $67 positive response to a service $27 (security access) diagnostic request. For example, $67 $01 $S1 $S2 $S3. Key (response) bytes are transmitted from R1 (most significant byte of the 3 byte key) to R3 (least significant byte of the 3 byte key) in a $27 submit key request. Integrity: the recipient ECU shall be able to verify that the original software has not been altered (e. g. manipulated by an unauthorized user) in transit. Copy Protection: it is used to prevent unauthorized feature activation, by e. g. copying a software from one ECU to another. This is not the same as encryption, for confidentiality. Copy protection is realized by key management. The two first terms, Authentication (proof of origin) and Integrity, are commonly referred to as Authenticity. It is accomplished by the use of public-key algorithms (asymmetric algorithms), where the key (private key) used to encrypt the software is separated from the key used to decrypt it (public key). The private ( secret) key is exclusively known to the originator of the software, thus this key is used for signing (generating a digital signature). The recipient(s) having access to the public key is able to verify the downloadable parts. The software together with the signature shall be sent to the recipient ECU. Standard code signing technology relies on asymmetric cryptography in the form of public key infrastructure (PKI) and provides a well proven quality history. To summarize: Software Authentication concept is applied to ensure that the software being executed in the vehicle is authentic by: Secure download/flushing (prevent "malware" software by verifying the downloaded software part). Focus of this specification. Secure boot (prevent from booting modified and unauthorized software)It does however NOT cover e. g. a secure delivery process of complete file from software supplier to the OEM but describes how to sign the data blocks of a software part once those criteria(s) for signing it are fulfilled. Hence, conditions to ensure that a software part is valid and trusted prior to it is stored in software archives, distributed to e. g. cloud etc. or for performing the actual signing of the data blocks are to be specified elsewhere.
