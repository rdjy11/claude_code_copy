### 1632 — No priority inversion
- 版本：v2 ｜ 验证方式：Analysis ｜ 适用：通用 ｜ Legacy ID：77275v1

The concept of guaranteed worst case latency offers several advantages to the system designer as well as to the node designer and node supplier. The SDB team will use guaranteed worst case latency to design a set of frames which will fulfil the signalling requirements given in the specifications defining vehicle functions. It will also be possible to guarantee that no signals will be overwritten, even when they have been transferred over gateways. Guaranteed worst case latency also permits busload to be significantly higher than the 30% often seen as the practical limit for reliable communication on CAN buses. The communication driver shall be designed to be free of priority inversion when frames are transmitted on the CAN bus by AUTOSAR based ECU's. If all CAN stacks are designed according to the priority inversion avoidance (PIA) concept it becomes possible to analyse the bus behaviour a priori. This analysis makes it possible to calculate and guarantee the worst case latency of all frames. ### 1640 — Diagnostic IP routing algorithm
- 版本：v3 ｜ 验证方式：Analysis ｜ 适用：通用 ｜ Legacy ID：342169v0

Clarification of how the diagnostic IP routing algorithm shall work. A general rule for the Edge Node to be able to decide what kind of diagnostic message which shall be send over the IP-links or other vehicle network (CAN, LIN, FlexRay) is to investigate the IP address and search for the Domain ID. If the three lowest nibbles of the ECU address matches the three lowest nibbles in an IP address, use this IP address when route/gateway diagnostic messages. Otherwise use the IP address of the domain master for diagnostic messages. (i. e. IP address that match ECU address [Domain ID].0.1). Example ECU: VGM (Edge node) has active DoIP TCP connections from [198.18.34.1] & [198.18.2.18]When a request for 0x1201 is received the following happens: 0x1201 means domain 2 => IP / Eth interface, The three lowest nibbles in 0x1201 matches the three lowest nibbles in 198.18.34.1 => use the connection with IP 198.18.34.1When a request for 0x1212 is received the three lowest nibbles in 0x1212 matches the three lowest nibbles in 198.18.2.18 => use the connection associated with IP 198.18.2.18When a request for 0x1241 is received the three lowest nibbles in 0x1241 does not match the three lowest nibbles in the IP address for any active connection => Try with the domain master address 0x1201 instead => 0x1201 matches the three lowest nibbles in 198.18.34.1 => use the connection with IP 198.18.34.1When a request for 0x1341 is received, domain 3 is still IP/Eth, the three lowest nibbles in 0x1341 does not match the three lowest nibbles in the IP address of any active connection => Try with the domain master address 0x1301 instead => 0x1301 does not match any active connection => Send DoIP Nack(Unknown Target Address) to tester.

### 1662 — Bootloader CAN busoff handling
- 版本：v2 ｜ 验证方式：Analysis ｜ 适用：通用 ｜ Legacy ID：392111v0

To increase availability of the system. Avoid that an ECU gets stuck in bus-off state, or exits programming session due to network errors. If hardware support automatic CAN busoff recovery, that recovery mechanism shall be enabled. If hardware doesn't support automatic bus-off recovery the bootloader shall check all active CAN controllers for bus-off status at maximum 10 ms intervals and if bus-off is detected start the bus-off recovery sequence within 10ms. This requirement applies to Primary Boot Loader (PBL) and Secondary Boot Loader (SBL). Note: If a permanent busoff condition is detected that can not be recovered, and a complete and compatible application exist, the S3server timer shall still run and will finally elapse, causing and exit of the programming session.
